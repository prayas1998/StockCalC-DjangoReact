# Rate limiting

The API middleware applies the configured auth, data-operation, and general limits with a rolling window. Counters are separated by category and by authenticated user ID or anonymous client IP. Accepted requests are counted; a per-key 429 reports the next request expiry, while a capacity 429 reports when the earliest bucket will fully expire. Per-process state is capped at 10,000 keys. When the cap is full, expired entries are reclaimed from an earliest-expiry queue; if all entries are still live, a new key receives 429 until the next key expires.

Before auth verification, requests with a Bearer header use trusted-IP budgets by category: 20/minute for auth, 1000/hour for data, and 2000/hour for general requests. These limits match the single-user ceilings, so one user's configured burst fits; together they bound auth-middleware verification admissions to 4200 per hour across categories. The counters aggregate all users behind the same IP, however, and can limit a group that shares an IP. They cap auth-middleware verification admissions per process before the provider call. No-Bearer requests skip this gate and continue to the configured anonymous limits. Invalid Bearer requests still count against the existing anonymous budget after verification fails; the preverification budget also bounds the provider calls that occur before those responses. Other route handlers may make additional Supabase Auth calls after middleware verification.

The process keeps a bounded cache of hashes for previously verified tokens, mapped to the verified user ID until token expiry. It never trusts an unverified subject claim and never skips auth verification. For a known token, it reserves the verified user's remaining local quota before calling Supabase; concurrent requests cannot all consume the same final slot. The reservation becomes the normal post-auth count before the handler runs, or is released if verification fails. A new token cannot be assigned to an existing user until Supabase verifies it, so its first lookup may still precede a user-budget rejection.

These are local safety ceilings only. Vercel can serve requests from different function instances and cold starts, each with independent memory, so these counters do not enforce a shared deployment-wide limit. A Node server uses the connection socket peer when available and does not trust caller-supplied forwarding headers. In the Vercel runtime, anonymous identity uses the first `x-forwarded-for` value (falling back to `x-real-ip`); [Vercel documents](https://vercel.com/docs/headers/request-headers) that it overwrites `x-forwarded-for` with the public client IP. Do not treat caller-supplied forwarding headers as trusted on a direct or differently proxied deployment.

## Production deployment gate

Before release, configure a Vercel WAF rate rule or another trusted shared limiter for the API. An IP-keyed WAF rule protects the function and Supabase Auth lookups before they run; it must use the platform-derived client IP. [Vercel documents](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting) that WAF rate-limit counters are tracked per region, so traffic in multiple regions can exceed the configured per-region limit. Do not describe that rule as a single global counter. If strict deployment-wide per-user limits are required, use an atomic store with that consistency scope; [Vercel's Rate Limiting SDK](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting-sdk) also allows a verified user ID key, but its counters are per region. No active or draft WAF rule was present in the latest deployment check, so hosted enforcement remains an open release gate.

Validate the deployed staging project with a synthetic client and no real user data:

1. Send requests just below and above the configured auth, data-operation, and general limits inside one window. Confirm the expected 200/429 boundary and the `retry_after` response value.
2. Repeat the burst while requests land on separate function instances and after a cold start. The shared edge/limiter must continue enforcing its configured budget.
3. From one client, vary caller-supplied `x-forwarded-for` and `x-real-ip` values during the same burst. Confirm the platform ignores or overwrites them and the effective client identity remains stable. If it does not, fix the trusted proxy configuration or use a platform-derived identity before release.
4. Verify authenticated requests are keyed by the verified user ID in the shared limiter when per-user deployment-wide budgets are required.

The repository does not configure or provision the shared edge/limiter service. Record the staging result and active rule/configuration in the release evidence; keep deployment on hold if these checks cannot be completed.
